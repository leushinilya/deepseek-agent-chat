# ИИ-агенты и сравнение моделей

Flutter-приложение объединяет исходный экран сравнения моделей с системой настраиваемых ИИ-агентов и отдельных чатов. Агенты, чаты и сообщения сохраняются локально через `shared_preferences`; запросы к моделям идут через Express backend, поэтому секрет DeepSeek не попадает в клиентский bundle.

Поддерживаемые модели:

- `GigaChat 3.1 (локальная)` — официальный Ollama Chat API;
- `deepseek-v4-flash` — DeepSeek API;
- `deepseek-v4-pro` — DeepSeek API.

## Конфигурация

Создайте `backend/.env` на основе `backend/.env.example`:

```env
DEEPSEEK_API_KEY=your_deepseek_api_key_here
DEEPSEEK_API_URL=https://api.deepseek.com/chat/completions
OLLAMA_BASE_URL=http://localhost:11434
LOCAL_MODEL=hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:Q4_K_M
PORT=3000
FRONTEND_ORIGIN=http://localhost:8080
```

`DEEPSEEK_API_KEY` нужен только для DeepSeek. Если он не задан, backend продолжит работать с Ollama, а в DeepSeek-чате появится понятная ошибка конфигурации. Никогда не передавайте этот ключ через `--dart-define` и не добавляйте `.env` в Git.

### RAG

Во вкладке «Настройки → RAG» создайте набор документов (TXT, Markdown, CSV, JSON или PDF),
выберите разбиение по фиксированному размеру или по структуре и нажмите
«Запустить индексацию». Для эмбеддингов backend использует Ollama и модель
`nomic-embed-text`. Перед первой индексацией загрузите её командой
`ollama pull nomic-embed-text`. Имя модели можно изменить через
`RAG_EMBED_MODEL`, адрес Ollama — через `OLLAMA_BASE_URL`, путь к базе SQLite —
через `RAG_DB_PATH` (по умолчанию `data/rag.sqlite`). Для backend нужен Node.js 22+.
Каждый чанк хранит `source`, `title`, `section`, `chunk_id`, текст и эмбеддинг.
Название RAG можно изменить в его карточке. Кнопка «Проверка» показывает
сохранённый локальный индекс: чанки с текстом и метаданными. Полный вектор
эмбеддинга открывается в отдельной карточке по нажатию на размерность;
длинный список чанков разбит на страницы.
Каждый RAG отображается отдельной карточкой; нажатие открывает документы и
настройки в диалоге. Кнопка удаления на карточке запрашивает подтверждение,
удаляет документы и индекс и отключает RAG от агентов в текущем профиле.
Для PDF извлекается текстовый слой; сканированные страницы без текстового слоя
потребуют предварительного распознавания текста. Количество и размер загружаемых
файлов приложением не ограничены.
После индексации откройте карточку агента. Кнопки MCP и RAG показывают выбранные
элементы и открывают списки с чекбоксами. Можно выбрать несколько RAG; при каждом
сообщении агента backend ищет по всем выбранным базам и передаёт модели
отобранные чанки с именами файлов и разделов. Для нового подключения
доступны только проиндексированные RAG. Это работает и в обычных, и в
запланированных чатах.

В карточке RAG поле «Промт RAG» задаёт инструкции для работы с этой базой
документов (до 10000 символов). Нажмите «Сохранить настройки поиска»:
промт сохраняется без переиндексации и учитывается в ответах обычных и
запланированных чатов, а также в обоих вариантах сравнения качества.
При нескольких подключённых RAG применяются промты каждой базы.
Пустое поле отключает дополнительные инструкции для этой базы.

### Настройки поиска и query rewrite

В карточке RAG блок «Поиск и релевантность» управляет поиском без переиндексации:

- «Переформулировать запрос» — модель, выбранная у агента, превращает последний
  вопрос в самостоятельный поисковый запрос с учётом последних сообщений,
  резюме и facts. Исходное сообщение пользователя остаётся в истории и передаётся
  модели для ответа. Кнопка «Поисковый запрос» в сообщении открывает rewrite
  и показывает, сколько фрагментов было отобрано для каждого RAG.
- «Фильтр по similarity» — после векторного поиска отбрасывает кандидатов
  с cosine similarity ниже порога. Равный порогу score проходит фильтр.
- «Top-K до отбора» — число кандидатов из каждого RAG (1–100, по умолчанию 20).
- «Top-K после отбора» — максимум фрагментов каждого RAG в контексте ответа
  (не больше top-K до отбора, по умолчанию 5).
- Порог similarity — число от −1 до 1, начальное значение 0.3. Это не вероятность
  правильного ответа: подходящий порог зависит от эмбеддингов и документов.
- «Соседей с каждой стороны» — после отбора добавляет 0–2 соседних чанка из того
  же раздела (по умолчанию 1). Повторяющиеся чанки передаются только один раз.
- «Дополнительных догрузок агентом» — до 0–5 вызовов инструмента для чтения
  продолжения раздела (по умолчанию 3). Агент может запросить только соседа уже
  переданного чанка.
- «Лимит контекста» — общий предел текста найденных и догруженных чанков одного
  RAG (1000–50000 символов, по умолчанию 20000).

Настройка количества новых поисков отсутствует: агент может выполнять дополнительные
поиски при каждом новом запросе пользователя независимо от прежнего лимита.
При каждом сообщении пользователя backend снова выполняет начальный поиск по
подключённым RAG. Если найденного недостаточно, агент может вызвать `rag_search`
для другого запроса, а затем при необходимости прочитать соседние чанки.
Повторные поиски используют текущие порог similarity, top-K и лимит контекста.
При индексации чанки связываются с предыдущим и следующим чанком того же раздела.
Для старых индексов эти связи появятся после повторной индексации. Настройки
подгрузки сохраняются без неё, но начинают работать только с новым индексом.

Векторный поиск использует формат входа, требуемый моделью эмбеддингов.
Для `nomic-embed-text` документы кодируются с префиксом `search_document:`,
а вопросы — `search_query:`. Модель и формат сохраняются в индексе: прежние
индексы без префиксов до переиндексации используют прежний формат вопроса.
После изменения модели эмбеддингов новый индекс нужно построить заново;
совпадение размерности векторов само по себе не означает их совместимость.

Структурное разбиение распознаёт номерные заголовки PDF, например
«13.9.1 Модели учета», сохраняет их в тексте фрагмента и не принимает
строки оглавления или ссылки «раздел …» внутри предложений за заголовки.
Для применения обновлённого разбиения и формата Nomic к прежнему индексу
запустите индексацию повторно. Поиск выполняется только по векторам.

Настройки сохраняются в SQLite отдельно для каждого RAG. Фильтр и rewrite
по умолчанию включены, в том числе у ранее созданных RAG. Если у агента выбрано
несколько RAG, rewrite выполняется один раз; каждый RAG использует свой порог,
лимиты и переключатель rewrite. Для RAG с выключенным rewrite поиск выполняется
по исходному вопросу. При отсутствии подходящих фрагментов модель получает
инструкцию сообщить о недостатке данных в документах. Ошибка rewrite отображается
как ошибка поиска; исходное сообщение сохраняется и запрос можно повторить.

В блоке «Сравнение качества» выберите агента и введите вопрос. Кнопка
«Сравнить» выполняет два прогона с одной моделью и системным промптом агента:
исходный вопрос без фильтра/rewrite (top-5) и поиск с параметрами формы.
Сравнение не сохраняет эти параметры в RAG.
Параметры контекста раздела для сравнения задаются отдельно: по умолчанию
соседей, догрузок и повторных поисков — 0, а лимит текста берётся из RAG.
Видны ответы, источники, оценки кандидатов,
отобранные фрагменты и время полного прогона. Rewrite и сравнительные ответы
используют temperature=0. Сравнение выполняется по документам открытого RAG;
историю конкретного чата, MCP и память оно не использует. Запросы к облачной
модели могут расходовать API-бюджет.

Для подбора порога проверьте один и тот же набор вопросов в обоих режимах:
точные вопросы по документам, вопросы с другой формулировкой, уточнения из
диалога (в чате) и вопросы без ответа в базе. Отмечайте правильность ответа,
наличие нужного источника и выдуманных фактов. Повышайте порог, если проходят
лишние фрагменты; снижайте, если отсеиваются нужные. Результаты сравнения
показываются в карточке до следующего изменения настроек или её закрытия.
Автоматической оценки ответов отдельной моделью нет: фактическое качество
нужно оценивать на вопросах и документах пользователя.

## MCP-серверы

Во вкладке «Настройки → MCP» создаются общие MCP-серверы. Затем в карточке агента
откройте редактирование и отметьте серверы, которые ему доступны. Привязанные MCP
показываются в карточке агента; к одному агенту можно подключить до пяти серверов.
Существующие привязки переносятся в общий список при первом запуске новой версии.

Для создания сервера «Файловая система» используется
[`@modelcontextprotocol/server-filesystem`](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem).
Укажите один или несколько абсолютных путей к каталогам **на машине backend**.
Пути можно ввести вручную или выбрать кнопкой с иконкой папки; окно выбора позволяет
перейти к любому каталогу, доступному backend.
Сохранённый путь можно изменить кнопкой редактирования рядом с сервером. Перед
сохранением приложение проверяет, что каталог существует и доступен backend.
Кнопка «Проверка» в карточке сервера выполняет `tools/list` и показывает полный
ответ MCP-сервера или ошибку подключения.
Сервер получает доступ только к выбранным каталогам и запускается для запросов чата
агента, которому он подключён. Backend должен иметь права ОС на эти каталоги.
Пакет устанавливается
при `npm install` в каталоге `backend`.

Также доступен тип «Чтение сайтов» на основе официального
[`mcp-server-fetch`](https://github.com/modelcontextprotocol/servers/tree/main/src/fetch).
На машине backend установите [uv](https://docs.astral.sh/uv/) и убедитесь, что
команда `uvx` доступна в `PATH`: сервер запускается как `uvx mcp-server-fetch`.
Он извлекает страницу по URL, который агент передаёт инструменту `fetch`, и
преобразует содержимое в Markdown. Сервер Fetch может обращаться к локальным и
внутренним IP-адресам, поэтому используйте его только с доверенными агентами и
запросами.

Когда у агента есть MCP-сервер, ответы чата формируются после выполнения вызовов
инструментов. Такие ответы появляются целиком после завершения вызовов, а не
постепенно по мере генерации.

Полный Ollama endpoint можно переопределить совместимой переменной `OLLAMA_API_URL`; обычно достаточно `OLLAMA_BASE_URL`. Адрес Flutter-клиента к backend задаётся через `--dart-define=API_BASE_URL=...`, по умолчанию `http://localhost:3000`.

## Ollama и локальная модель

1. Установите и запустите [Ollama](https://ollama.com/).
2. Загрузите модель, указанную в `LOCAL_MODEL`:

```powershell
ollama pull hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:Q4_K_M
```

3. Если Ollama не запустилась автоматически:

```powershell
ollama serve
```

4. Проверьте установку:

```powershell
ollama list
```

Для другого тега/квантизации измените только `LOCAL_MODEL` в backend-конфигурации. Внутренний клиентский идентификатор `local-gigachat` при этом остаётся стабильным.

## Стратегии контекста чата

В шапке чата можно выбрать режим управления контекстом:

- **Полная история** — в запрос передаются все сообщения;
- **Compression** — ранние сообщения заменяются обновляемым резюме;
- **Sliding Window** — в запрос передаются только последние `N` сообщений;
- **Sticky Facts** — после каждого сообщения пользователя модель обновляет
  отдельный JSON-блок facts, а в ответ идут facts и последние `N` сообщений;
- **Branching** — кнопка создаёт checkpoint в текущей точке и две независимые ветки.
  Выбор ветки меняет активную историю, а новые сообщения не затрагивают другую ветку.

Вся история, facts, checkpoint, ветки и настройки `N` сохраняются локально
отдельно для каждого чата. Sticky Facts, как и резюме, требует дополнительного
запроса к выбранной модели.
В Sticky Facts факты отображаются в отдельной карточке справа. В Sliding Window неиспользуемая
часть истории свёрнута; её можно развернуть, при этом исключённые сообщения визуально выделены.

## Модель памяти

Реализованы три независимых типа памяти с отдельными областями управления:

```text
Проект (1) ──< Задачи (много) ──< Чаты (много)
ИИ-агент (1) ───────────────────< Чаты (много)
```

Для задачи обязательно выбирается проект. Для чата независимо выбираются
ИИ-агент и задача. Поэтому чат использует системный промт выбранного агента,
долговременную память проекта своей задачи и рабочую память самой задачи.

- **краткосрочная** — сообщения текущего диалога; это сам чат, дополнительных
  настроек для неё нет;
- **рабочая** — цели, ограничения и состояние текущей задачи; управляется во
  вкладке «Задачи» и разделяется всеми чатами этой задачи;
- **долговременная** — профиль, принятые решения и знания проекта; управляется
  во вкладке «Проекты» и доступна чатам всех задач этого проекта.

Рабочие и долговременные записи можно добавлять и удалять. Обычное сообщение
попадает только в историю текущего диалога и не переносится автоматически в
другие виды памяти. Данные физически разделены ключами
`memory_short_term_v1_<chatId>`, `memory_working_v1_<taskId>` и
`memory_long_term_v1_<projectId>`. Перед запросом к модели три блока памяти
передаются независимо. Агент хранит только системный промт и настройки модели.

### Compression

Выберите стратегию «Compression» и задайте целые числа
`1 ≤ min < max` (по умолчанию `max = 20`, `min = 6`). Настройки сохраняются
отдельно для каждого чата. Перед запросом к модели учитывается новое сообщение
пользователя: при достижении `max` несжатых сообщений выбранная модель создаёт
резюме более ранней переписки, оставляя последние `min` сообщений целиком.
При следующем сжатии предыдущее резюме обновляется.

Полная история сохраняется в локальном хранилище. В интерфейсе сжатые сообщения
сворачиваются в блок с резюме и кнопкой «Показать исходные сообщения»; их можно
раскрыть и снова скрыть. После нового сжатия блок снова сворачивается. Счётчик токенов
учитывает активный контекст. Отключение функции возвращает полную историю
в запросы к модели. При ошибке или остановке сжатия можно нажать «Повторить»;
частичное резюме не сохраняется. Сама суммаризация требует отдельного запроса
к выбранной модели и расходует токены.

## Запуск приложения

```powershell
cd backend
npm install
npm run dev
```

В отдельном терминале из корня проекта:

```powershell
flutter pub get
flutter run -d chrome
```

Для production-развёртывания ограничьте `FRONTEND_ORIGIN` реальным origin приложения и храните `DEEPSEEK_API_KEY` в защищённой конфигурации сервера.

## Проверки

```powershell
flutter analyze
flutter test
flutter build web
cd backend
npm test
```

Тесты используют подменяемые хранилища и LLM-провайдеры, поэтому реальные API для них не требуются.
